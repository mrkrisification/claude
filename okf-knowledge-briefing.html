From retrieval to compiled knowledge
01 / THE SHIFT

The paradigm today — RAG

Stateless retrieval
  • Documents are dumped into a vector database; at query time the model searches for relevant chunks.
  • The LLM rediscovers knowledge from scratch on every question — there is no accumulation.
  • Subtle questions that need five documents must be re-pieced together every single time.

The shift — a compiled wiki

Stateful, compounding
  • A set of human-readable, LLM-maintained markdown files — one per concept.
  • Cross-referenced, with provenance and version history via git.
  • Pay the compilation cost once; queries are cheap and accurate because the thinking is done.
"Knowledge as compiled code: your raw docs are the source files; the wiki is the binary."
Why it struck a nerve — LLMs don't
find the bookkeeping tedious.

What OKF actually is
02 / THE SPEC · v0.1
01
Format, not platform
A directory of markdown files with YAML frontmatter. cat a file to read it; git clone to distribute. No SDK, no registry, no central authority.
02
One required field
Every concept needs exactly one thing — a type: field. Everything else is left to the producer.
03
Two reserved filenames + a graph
index.md (listing) and log.md (history). Concepts cross-link with bundle-relative markdown links — the directory becomes a graph.
04
Deliberately permissive
Unknown types and fields are preserved on round-trip; missing optional fields, unknown types and broken links never cause rejection.
A concept document
--- type: BigQuery Table title: Customer Orders description: One row per completed customer order. resource: https://… tags: [sales, orders] --- # Schema # Examples # Citations
Producer / consumer are independent: a human-authored bundle is consumed by an agent. The format is the contract.

Karpathy × OKF — workflow + format
03 / THE COMBINATION

Karpathy's gist → how to behave

The workflow
  • Ingest — read a new source, integrate it into existing pages.
  • Query — answer from the already-synthesized wiki, no re-chunking.
  • Lint — audit for contradictions, orphans, missing links.
  • An idea file, not a spec — every team's instance is bespoke and doesn't interoperate.

OKF's spec → how to format

The file format
  • Frontmatter with type, reserved filenames, link conventions.
  • The minimum standardization needed for interoperability.
  • The interoperability bet: producers and consumers converge → knowledge stops being siloed.
Hand the agent both in one CLAUDE.md: Karpathy = behaviour, OKF = schema.
The only real delta OKF adds
is the frontmatter block.

Each KB is a single-purpose OKF bundle. The agent reads the meta index.md, dives into the relevant sub-bundle, and follows links down to raw/ when it needs the original source.
Decisions worth making explicit
①
Ownership. One person / small group per KB feeds sources, triggers ingest, lints. Without it, wikis rot.
②
Cross-KB linking. OKF doesn't define it — set your own convention in the meta CLAUDE.md.
③
RAG as overflow valve. Layer it over compiled pages for cross-KB synthesis — complement, not replacement.
④
The real risk. Whether owners actually maintain their KBs — not the architecture itself.

Will OKF become the standard?

Bet on the pattern,
not the brand.

Uncertain as a named spec — but the underlying bet (markdown + git as the substrate for agent-readable knowledge) looks solid, and migration between markdown standards is an afternoon of find-and-replace.

Likely outcome
Loose convergence — like REST. type: frontmatter and index.md / log.md as de-facto conventions.
Why it sticks
Every major agent already reads local markdown; git gives history for free; adoption cost ≈ zero.
The real risk
Not picking the wrong standard — picking no structure and keeping the wild fileshare.
For the initiative
Small owned KBs + meta-layer · wiki for knowledge, MCP/DB for live data · start report-only.
